# Retrieval evaluation

Run `bun run evaluation:check`. This executes production retrieval operations against disposable Git brains and PGLite projections. It never consults an existing archive, user configuration, hosted service, or model. A failed fixture setup or unexpected operation error fails the run; authorization errors count as expected denials only for the explicitly denied tenant case.

`retrieval-baseline.json` retains the original six-query baseline. `retrieval-baseline-v2-before-safety.json` records the first executed lifecycle corpus before safety fixes: each split scored 0.90909 on recall@10, MRR, and nDCG@10, returned one stale source, and produced three citations rejected by the shared evidence validator. Two were memory recall citations lacking chunk/schema fields; one was stale evidence. The temporal role filter also missed `User:` transcripts.

`retrieval-baseline-v2.json` records the same corpus after those fixes. Both development and held-out splits contain 29 executed queries, with separate metric gates. The corpus hash covers all source text, validity boundaries, query expectations, lifecycle phases, graph policy, and fixture parameters. Changing that hash requires an explicit baseline review; the check never rewrites baselines.

The fixtures cover cross-session ownership and decisions, noisy tool transcripts, temporal and role filters, exact citation verification, unauthorized tenant and visibility access, stale sources, expired and future memories, corrections, withdrawals before projection refresh, full projection rebuild, permission changes, duplicate capture after withdrawal, aliases, private intermediate entities, and one-, two-, and three-hop relationship chains. Generated answers are present as distractors and excluded from primary evidence.

Recall@10, MRR, and nDCG@10 use binary relevance over positive search/recall cases, deduplicated by stable document ID. Relationship queries have a separate exact predicate-chain match rate, including empty results for privacy and hop bounds. Empty retrieval cases form a zero-tolerance forbidden-result gate. Every returned search, recall, edge, and destination-entity citation is checked against current canonical Git with the production evidence validator. Withdrawal suppression on a deliberately outdated projection and idempotent replay after withdrawal are additional mandatory checks.

These small fixed suites provide deterministic regression checks. They do not estimate broad real-world relevance or local-model quality. No ranking feedback is enabled. Generation quality, configured-model latency, and real Codex/Claude session behavior require separate measurements; passing lexical fixtures does not establish those outcomes. When changing ranking, use development results for iteration and inspect held-out results only for acceptance.

Run an explicit local-model smoke benchmark with `bun run scripts/evaluate-local-generation.ts LOCAL_MODEL`. It creates a disposable Git brain and PGLite store, exercises production grounded answers, and removes the fixture afterward. It never reads owner configuration or archives. The fixed endpoint is loopback Ollama; no hosted fallback is used.

The recorded [local generation run](local-generation-evaluation.json) used installed `qwen3.8:27b`: all four synthetic cases passed, covering ordinary ownership, a database fact, a superseding correction, and refusal after withdrawal. End-to-end latency was 10.9–21.6 seconds, including model loading on the first request. Phrase checks and production citation validation do not establish semantic grounding for arbitrary answers. `seedFixtureHash` identifies the two seed records; the script also defines correction and withdrawal lifecycle steps. This report is separate from deterministic retrieval gates.

That run exposed full-question lexical misses. Grounded answers now try the exact query first, then fuse at most eight keyword searches when it returns no evidence. Every fallback result passes the same authorization, current-revision, withdrawal, and citation checks. The original question remains intact for generation. Keyword fallback can retrieve partial matches; the local model must report insufficient evidence when those do not answer the question.
