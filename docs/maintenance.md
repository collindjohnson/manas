# Canonical maintenance scans

Owner commands use the same catalog and configured engine as the service:

```sh
manas maintenance scan --input '{"maximumItems":100}'
manas maintenance scan --input '{"dryRun":true}'
manas maintenance proposals --input '{"limit":50}'
manas maintenance accept --input '{"id":"PROPOSAL_ID","expectedRevision":"REVISION","idempotencyKey":"review-approval-1"}'
manas maintenance dismiss --input '{"id":"PROPOSAL_ID","expectedRevision":"REVISION"}'
```

The scan returns a job. Inspect it through jobs list and run the configured service worker (or jobs run-one). Generic MCP grants cannot invoke these local owner operations. TypeScript callers may use maintenanceScanHandler, maintenanceProposals, and dismissMaintenanceProposal from the package root.

Scans inspect current canonical Git records. Exact content-hash duplicates produce review proposals. Typed entity and relationship citations are checked against current evidence and validity dates; changed, withdrawn, or expired evidence produces stale-evidence proposals. Potential contradictions between overlapping functional assertions produce separate review proposals. Missing and stale pinned answers enqueue the existing grounded answer refresh worker.

When a local generation model is configured, changed source revisions can produce fact-extraction proposals containing exact source spans. The model may select at most ten spans of at most 2,000 UTF-16 characters. Bounds and Unicode integrity are checked, and every selected span receives the shared document/revision/commit/span citation. Relationship findings also carry exact spans for subject, predicate, and object, inferred entity types, confidence, and optional validity dates that must appear literally in the cited source. Findings enter review by default. The source offsets establish provenance; model quality is evaluated separately.

Owner fact-span extraction covers plain notes without a source descriptor and active manas memories. Other primary records, including Google mail, calendar, and contacts records, can produce attributed relationship proposals; their assertions are not converted into owner fact spans. Canonical conversation ingestion records a hash-bound map of user-turn offsets from structured adapter messages. Maintenance analyzes only those user ranges, excluding assistant messages, spoofed role labels, Notes, and preserved legacy content. Missing or invalid maps fail closed; legacy archives and unknown manas-managed source types remain excluded until structured re-ingestion provides verified roles. Opt-in agent user-turn capture remains a separate flow. Large sources are processed in windows of at most 16,000 UTF-16 characters, with up to 2,000 characters of lookahead and disjoint ownership by assertion start offset. Window boundaries preserve Unicode characters and never cross user-turn boundaries. Citations retain full-document offsets. Generated answers, graph records, pinned questions, reviews, and maintenance proposals never become primary evidence or extraction inputs.

Analysis is frozen in operational state under tenant, brain, document, revision, and analyzer identity (policy plus provider fingerprint, falling back to model ID) and exact window bounds before any Git proposal is written. Repeated scans reuse it. Each window completes only after all of its proposals persist. Later windows have separate fact-proposal keys, so a completed first window cannot suppress later findings. Provider changes reuse existing proposal identities and dismissals; legacy document-wide fact proposals retain their original scope. The completion checkpoint advances after proposal persistence. A crash after the Git commit replays the same proposal key without a second commit. PostgreSQL migration 30 adds this tenant- and brain-isolated analysis journal; it is included in operational backups.

Proposals are Git-backed manas-owned records with stable keys derived from kind and exact source revisions. Source visibility labels are preserved. Dismissal requires the current proposal revision and persists suppression for those evidence revisions. Scans never delete, merge, correct, or withdraw source records. Owner acceptance of a current relationship proposal creates at most two cited entities and one typed relationship, reusing unambiguous existing entities. Approval requires the current proposal revision and an idempotency key scoped to that proposal. A graph commit followed by a receipt failure reuses the verified existing edge on retry. Ambiguous identity or type remains in review; use the typed entity review and relationship operations to resolve the intended identities. Accepted proposals retain approval receipts, and subsequent management uses the typed graph lifecycle. General page operations cannot overwrite managed proposals.

Proposal listings revalidate citations and current source revisions. If a source changes or a memory is withdrawn, only stale metadata is returned; historical assertion text is withheld. Rebuilding projections cannot restore that text. All maintenance proposals are excluded from primary retrieval.

Each job freezes a revision plan and saves its cursor after processing each item. It checks and renews its exact queue attempt's lease before writes; cancelled, expired, or replaced attempts fail the next lease check. A bounded Git write already begun may finish; cancellation does not undo committed proposals. A job inspects at most maximumItems work units (a page inspection or extraction window; 1–500, default 100) or about two minutes of work, whichever comes first. Model calls have a sixty-second timeout and a 16,000-character output cap. Durable continuation jobs retain the last fully processed ID. An unfinished source stays eligible, resumes from its first uncompleted window, and advances the page cursor only after its final window. A crash after a later-window Git commit replays its frozen findings without duplicate proposals. Plans exceeding 10,000 records fail with an explicit budget error. A record changed during a scan is skipped and reconsidered by a later scan.

Dry runs perform deterministic inspections and save queue progress, but do not invoke inference, create proposals, persist analysis, or queue pinned refreshes. With no local model, normal scans still perform duplicate/staleness checks and report extraction unavailable in progress. Explicit fact-extraction and entity-enrichment jobs require a configured local model and report the standard actionable configuration error otherwise.

The configured runtime routes maintenance-scan, fact-extraction, entity-enrichment, contradiction-analysis, deduplication, staleness-analysis, and dream-maintenance jobs through this scan. Legacy supplied facts or findings are not trusted inputs to those handlers. The older maintenance.propose compatibility operation remains a supplied-finding preview. Contradiction analysis compares current extracted relationship assertions with matching subjects and functional predicates (owner is, is owned by, is based in, is located in, deadline is, birth date is, date of birth is), different objects, and overlapping validity. These are potential conflicts for owner review, not automatic corrections. General natural-language contradiction classification remains future work. The comparison budget is 2,000 proposals and 10,000 pairs.

The existing automation.managedWrites setting may enable bounded automatic application of new relationship proposals. Both the proposal and any reused entities must have confidence of at least 0.9, identity must be unambiguous, and known functional conflicts remain in review. The setting is checked before every graph mutation. Revocation stops the next mutation without undoing already committed manas-owned entities; retry resumes from the same frozen analysis. Source corrections, merges, withdrawals, and destructive actions remain explicit owner workflows. A new model's confidence score does not silently replace or promote an existing proposal for the same source assertion.

For recurring scans, use the existing owner jobs schedule operation with type maintenance-scan, the configured brainId in its payload, and an intervalSeconds. The scheduler coalesces missed occurrences after resume. Only one service owns the local queue.

Maintenance requests JSON mode from compatible local generation providers and validates the complete response before journaling it. A single surrounding JSON code fence is accepted for custom providers; arbitrary commentary or malformed JSON fails without proposals. See the supported response format in the [Ollama compatibility reference](https://docs.ollama.com/api/openai-compatibility). Run `bun run scripts/evaluate-local-maintenance.ts LOCAL_MODEL` for an isolated real-model smoke check. It never reads owner configuration or real archives.

The [recorded local maintenance check](local-maintenance-evaluation.json) used installed `qwen3.8:27b` and completed in 19.7 seconds. It proposed one exact fact span and one attributed relationship for the synthetic note, both pending owner review and verified against Git. This single-note smoke check does not estimate broad extraction quality.
